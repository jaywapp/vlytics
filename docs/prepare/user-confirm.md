# 사용자 결정 사항

작성일: 2026-09-19 · 결정 원천: [원문](../ideas/vlytics.md), [검토 의견](../ideas/vlytics-claude-feedback.md)

이 문서는 제안을 사용자 승인으로 간주하지 않기 위한 결정 장부다. `Pending`은 미결정, `Confirmed`는 사용자의 명시적 결정 완료, `Deferred`는 해당 단계에서 다루지 않음을 뜻한다. UC-001~009는 2026-09-19 사용자 인터뷰로 Confirmed되었고 UC-010은 Deferred다. 각 항목의 추천은 결정 이전 제안이며, 최종 사용자 결정이 우선한다. 원문 10절의 남녀부·3계층·독립 AI 예측·T-60·전체 예측 종류·외부 Market 후행 비교·개인용 MVP는 계속 기준으로 삼는다.

자료에 적힌 API·시즌 수·경기 수·일정·성능·약관 설명은 제공 문서의 과거 관측 보고이며 이번 작업에서 재검증하지 않았다. 일정과 성능 숫자를 승인 조건이나 납기 약속으로 사용하지 않는다. 2026-09-20 후속 준비 작업에서 이 결정에 맞춰 design.md·architecture.md·plan.md와 UI 선택 표기를 동기화했다.

## UC-001 — MVP 전체 범위와 단계적 제공

**배경:** 원문 MVP는 선수/세트 feature, 네 가지 예측, Multi-AI, 자동 평가와 Web을 포함한다. 검토 의견은 snapshot 수집을 먼저 가동하고 화면·Market·점수 모델을 뒤로 미루자고 제안한다. 후자는 원문 확정 결정을 자동 대체하지 않는다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. 원문 전체 MVP를 한 번에 제공 | 초기 완료 시 모든 사용자 흐름 충족 | 점수 모델/Market/화면 의존으로 운영 시작 지연 가능 |
| B. 전체 목표 유지, 수집·불변 예측 → 평가·Web·Market → 점수 모델로 단계 제공 | 빠르게 전향 관측 확보, 단계별 검증 가능 | 초기 제공은 전체 MVP가 아니며 미지원 target을 명시해야 함 |
| C. 수집/예측 저장만 첫 제품으로 범위 재정의 | 가장 작은 초기 작업량 | 원문 기능/운영 경험 축소, 별도 재기획 필요 |

**추천(결정 전 제안):** B. 단, 각 단계의 기능·완료 기준과 점수 핸디캡/O-U 제공 시점을 승인받는다. 승인 전 plan의 후순위는 실행 순서 제안이며 기능 삭제가 아니다.

**결정 영향:** 기획의 출시 범위, architecture 모델 capabilities, 화면 준비 시점, plan의 critical path와 완료 판정.

**현재 상태:** Confirmed. **사용자 결정:** A (2026-09-19) — 원문 전체 MVP를 한 번에 제공한다. 선수/세트 feature, 네 가지 예측, Multi-AI, 자동 평가, Web UI 등 정의된 전체 사용자 흐름을 첫 MVP에 포함한다.

## UC-002 — 데이터 이용 범위와 실제 소스 커버리지

**배경:** 제공 검토는 공개 응답과 약관 일부를 보고했지만 자동 수집·재배포 권한이나 전체 상세 데이터 완전성을 보장하지 않는다. 세트별 선수 기록, 랠리, T-60 명단은 미확인이다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. 허용 범위 확인 후 KOVO 직접 수집 | 원문 목적과 직접 연결, raw lineage 확보 | 권한/요청량/정정/누락 조사 필요 |
| B. 승인된 파일·라이선스 데이터 공급원으로 시작 | 수집 조건을 명확히 관리 | 비용·범위·공개 시각 제약, KOVO 매핑 필요 |
| C. 합성 fixture로 구조만 준비하고 실수집 보류 | 외부 이용 결정 없이 검증 가능 | 실데이터 coverage/모델 성능 검증 불가 |

**추천(결정 전 제안):** C로 비의존 준비를 계속하면서 A의 허용 범위·요청 속도·사용 기간·보존/공개 조건을 문서화한다. 이용조건 읽기, 소스 조사와 계약 설계는 진행 가능하나 미확인 대량 backfill은 차단한다. 사용자 동의만으로 제3자 권리가 해결된다고 보지 않는다.

**구현 시 구체화:** 승인 근거, 소스/시즌/종류별 수집 범위, 실패/누락 수용 조건, bulk 요청 정책, player_set/랠리 보류 여부. 확인되지 않은 수치는 0으로 대체하지 않는다.

**결정 영향:** Collector 활성화, raw 보관, 실제 fixture, backfill 완료 기준, source_coverage·feature capabilities. **현재 상태:** Confirmed. **사용자 결정:** A (2026-09-19) — 이용 가능 범위를 확인한 뒤 KOVO 데이터를 직접 수집한다. 실제 대량 수집 전 이용 조건·요청량·coverage를 확인하며 미확인 값은 0으로 대체하지 않는다.

## UC-003 — 실행 환경·저장 방식·기술 스택

**배경:** 개인용이지만 경기 전 시각에 계속 실행되어야 한다. 물리 DB와 호스트는 원문 미결정이다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. 상시 호스트의 Python/FastAPI + PostgreSQL + React/TypeScript, 모듈형 모놀리스 | 분석 친화적, 영속 스케줄·권한·백업 일관성 | 서버 비용/운영, 두 언어 관리 |
| B. 동일 스택을 개인 PC에서 실행 | 초기 호스팅 비용 절감 | 절전·종료·재부팅 때 예측 누락, 운영 책임 큼 |
| C. 기존 선호 스택·관리형 서비스 조합 | 기존 지식/계정 활용 가능 | 설계 수정, 스케줄 제약·비용 재검토 |

**추천(결정 전 제안):** A. provider/worker/API를 별도 마이크로서비스로 나누지 않고 한 DB의 논리 스키마로 분리한다.

**구현 시 구체화:** 호스트/예산, 네트워크 접근 방식, DB와 원문 저장, 백업 보관 기간·RPO/RTO, 운영 인증·알림 채널. 런타임 정확한 버전은 구현 시작 시 검증해 잠근다.

**결정 영향:** 프로젝트 scaffold, 배포·CI, 스케줄러, SQL migration, 운영 비용과 접근 보안. **현재 상태:** Confirmed. **사용자 결정:** A (2026-09-19) — 상시 호스트에서 Python/FastAPI + PostgreSQL + React/TypeScript 기반 모듈형 모놀리스로 운영한다.

## UC-004 — 통계 기준선과 공통 확률 출력

**배경:** 원문은 네 종류 예측을 확정했지만 모델/출력 schema는 미정이다. Elo만으로는 세트스코어·점수 target을 완성하지 못한다. 총점만으로 점수 득실차도 알 수 없다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. Elo 승패 → 6개 세트 결과 분포 → 공동 점수 분포를 단계 추가 | 설명/검증 용이, 각 모델 역량을 구분 | 초기 미지원 target 존재, UC-001 단계 승인 필요 |
| B. 처음부터 세트별 점수 생성 모델과 공동분포 | 승패/세트/총점/득실차의 일관성 | 모델 검증·꼬리 분포·계산 부담 증가 |
| C. 독립 target별 모델·AI 출력을 각각 유지 | target별 유연성 | 승패·세트 결과 불일치, 평가·보정 복잡 |

**추천(결정 전 제안):** A의 공통 분포 schema와 capability 명시. 전체 MVP 완료 전 필요한 점수 모델을 추가한다. 점수 handicap은 `P(home_points, away_points, set_score)`나 동일 정보를 주는 세트별 시뮬레이션에서 도출한다. 세트 수별 총점 모델만 있으면 O/U까지 지원하고 점수 handicap은 미지원으로 남긴다.

**구현 시 구체화:** 기준선 후보·6범주 schema, 모델 단계·학습 구간·hyperparameter 선택, 성능 평가법, AI confidence의 참고 표기. 검토의 Elo 수치는 재현 목표 후보이며 보장 합격값이 아니다.

**결정 영향:** provider contract, feature 설계, Market 지원 범위, model registry, 평가/대시보드 지표. **현재 상태:** Confirmed. **사용자 결정:** A (2026-09-19) — Elo 승패에서 6개 세트 결과 분포, 이후 공동 점수 분포로 확장하는 공통 확률 구조를 사용한다. 최종 MVP에서는 네 종류 예측을 모두 제공한다.

## UC-005 — 외부 Market 계약

**배경:** Market 자체 수집은 확정된 범위 밖이다. 외부 DB의 실제 접속/단위/정산 규칙은 아직 없다. 라인은 모델 입력으로 주지 않는다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. full-match 승패/세트 handicap·total부터 계약 확정, 점수 target 확장 | 세트 모델과 조기 연결, 정산 단순 | 점수 기반 시장이 주 소스면 활용 제한 |
| B. 처음부터 점수/세트와 특례 시장을 모두 계약 | 실제 외부 시장 범위 폭넓게 수용 | 공동 점수 모델·quarter line·무효 규칙 구현량 큼 |
| C. 실제 schema 제공 전 비교를 missing 처리 | 독립 예측을 계속할 수 있음 | 시장 기준선·시장 적중률 실검증 불가 |

**추천(결정 전 제안):** 외부 적재자의 실제 계약을 먼저 확인해 A 또는 B 범위를 결정한다. 그 전에는 C 상태와 합성 fixture만 사용한다. 세트 기준 시장이 존재한다고 추정하지 않는다.

**구현 시 구체화:** 공급원/연결 방식·권한, source_event 매핑, line 단위/기간/부호, odds 형식, quote·수신 시각, max_age, 정산·push·void·몰수·재편성, 부분경기/quarter line 지원 여부.

**결정 영향:** market schema, 후행 확률 계산, snapshot eligibility, 시장 기준선 cohort·화면 결측 사유. **현재 상태:** Confirmed. **사용자 결정:** C (2026-09-19) — 실제 외부 Market schema가 확보되기 전까지 Market 비교 데이터는 missing 처리한다. 기능·contract/interface·합성 fixture는 MVP 범위에 유지한다.

## UC-006 — AI 역할·Provider·비용·버전 정책

**배경:** 독립 AI 예측과 GPT/Claude/Gemini 교체 가능 구조는 확정이다. 실제 사용 모델/변형 수·예산은 미정이며 검토의 보정자/설명 전담 제안은 기존 역할을 대체하지 않는다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. 독립 예측 유지, 적은 수의 고정 모델/프롬프트로 시작 | 원문 부합, 공정한 전향 짝비교 | 숫자 feature만으로 AI 우위 불확실 |
| B. A + 통계 확률을 받는 보정 실험군 | 증분 효과를 같은 경기에서 측정 | 추가 비용·다중 비교·입력 그룹 구분 필요 |
| C. A + 승인된 비정형 정보 실험군 | AI가 활용할 추가 정보 확보 | 별도 수집권한·as-of·편향 관리 필요 |

**추천(결정 전 제안):** A. 어댑터 구조는 세 Provider를 지원하도록 설계하되 실제 활성 모델과 호출 수는 명시적으로 선택한다. B/C는 추가 승인을 받은 실험군으로만 도입한다. 설명 전담으로 독립 예측을 대체하려면 원문 요구 변경으로 따로 기록한다.

**구현 시 구체화:** provider/model ID, 날짜 고정 버전 가능 여부, alias 대체 규칙, 월/일 비용 한도·변형 수, timeout/token cap, 응답 원문 보관, prompt 변경 시 동시 비교 기간. 예산 초과는 `budget_skipped`로 남기고 baseline은 계속한다.

**결정 영향:** adapter 구현·secret 설정·model registry·cohort·대시보드 비용/실패, live 전향 비교. **현재 상태:** Confirmed. **사용자 결정:** A (2026-09-19) — GPT/Claude/Gemini의 독립 예측을 유지하고 소수의 고정 모델·프롬프트로 시작한다. 실제 모델 ID·호출 수·예산은 구현 시 명시적으로 고정한다.

## UC-007 — T-60 실행·늦은 완료·최종 결과 정정

**배경:** 원문은 T-60 최종 분석을 확정했다. 피드백의 T-10까지 재시도는 새로운 제안이다. 입력 고정 시각, 호출 시작, 응답 완료는 같은 시각이 아니다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. T-60 기준의 엄격한 실행 허용 오차·짧은 grace | 동일 시점 비교가 명확 | 장애·느린 응답으로 표본 누락 증가 |
| B. T-60 입력 고정, T-10까지 시도/완료 허용 | 일시 장애 복구 가능 | late_pregame 별도 표기·비교, 원문 운영 규칙 변경 승인 필요 |
| C. 경기 시작 전까지 유연한 재시도 | 가용 표본 최대화 | 시점 불균형·운영/해석 복잡, 최종 분석 의미 약화 |

**추천(결정 전 제안):** A를 원문 기준으로 유지하면서 짧은 grace 수치를 결정한다. B를 선택하면 입력은 T-60 그대로 고정하고 `on_time`/`late_pregame` cohort를 분리한다. 어떤 안도 경기 후 완료 응답을 유효 예측으로 인정하지 않는다. T-10은 승인 전 기본값이 아니다.

**구현 시 구체화:** 허용 오차·retry/response deadline, 실제 시작 미확인 시 처리, 연기/재편성 새 snapshot 정책, provisional→final 안정화 간격, 정정 재동기화 기간과 성능 갱신 기준. 권고는 원문 예측 불변 + append-only void/supersede 이벤트, 정정 결과별 새 evaluation이다.

**결정 영향:** scheduler, 시계/재시작 검증, 평가 적격성, history 상태와 dashboard 분모. **현재 상태:** Confirmed. **사용자 결정:** A (2026-09-19) — T-60 엄격 실행과 짧은 grace를 사용한다. 정확한 grace/retry/deadline 수치는 구현 단계에서 확정하며 경기 시작 후 완료 응답은 유효한 사전 예측으로 인정하지 않는다.

## UC-008 — UI 시안 선택

## UC-009 — 대회 범위·구단 연속성·과거 가용시점 가정

**배경:** 남녀부 지원은 확정이지만 정규/PO/챔프 집계와 팀 인수·시즌별 제도 처리는 미정이다. 현재 backfill로 당시 관측시각을 복구할 수 없다. 피드백의 구단 변경 사례는 조사할 예시이며 이번에 재확인한 사실이 아니다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| A. 정규리그 우선, PO/챔프 별도 cohort; 검증된 franchise mapping; 과거는 reconstruction 표시 | 해석·비교 명확, 과거 데이터를 제한적으로 활용 | 매핑/가정 관리와 대회별 적은 표본 |
| B. 모든 대회를 통합하고 source team code로 단순 구분 | 초기 구조 단순 | 대회 차이·인수/개명·제도 변화가 성능에 섞임 |
| C. 당시 관측 자료가 있는 구간만 strict 평가 | as-of 신뢰도 높음 | backfill 대부분을 예측력 평가에 사용하지 못할 수 있음 |

**추천(결정 전 제안):** A, 추가로 실제 시점 자료가 확보된 구간은 C의 strict cohort를 병기한다. 올스타/시범 제외는 추천이며 사용자 선택 전 원문에서 확정했다고 쓰지 않는다. 남녀 모델/집계는 분리한다.

**구현 시 구체화:** 허용 대회, 구단 인수 시 Elo 이월/추가 회귀, 시즌별 규칙/경기장 매핑, historical availability policy, roster/정정 시각을 모르는 자료의 제외 기준.

**결정 영향:** identity resolver·Elo 이월·source coverage·백테스트 split·성능 cohort·필터. **현재 상태:** Confirmed. **사용자 결정:** A (2026-09-19) — 정규리그 우선, PO/챔프는 별도 cohort로 관리한다. 남녀부를 분리하고 검증된 franchise mapping을 사용하며 과거 재구성 데이터는 reconstruction, 당시 시점 자료가 있는 구간은 strict cohort로 관리한다.
